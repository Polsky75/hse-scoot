# 002. Три вида транспорта и фабрика NewTransport

- **Дата:** 2026-10-25
- **Статус:** принято

## Контекст

Парк состоит из самокатов, велосипедов и электровелосипедов. Видов должно
становиться больше без переписывания прикладного слоя. Велосипед не
потребляет электроэнергию, поэтому не должен вести себя как `IConsumptor`:
нулевой расход у велосипеда скрыл бы разницу между «не потребляет» и
«потребляет ноль».

## Решение

- Введён строковый тип `domain.TransportKind` с константами
  `KindScooter`, `KindBicycle`, `KindEBike`.
- `Scooter` и `EBike` встраивают `electricDevice` и реализуют `ITransport`,
  `IInventoriable` и `IConsumptor`.
- `Bicycle` встраивает `transportDevice` и реализует `ITransport`
  и `IInventoriable`, но не `IConsumptor`.
- `domain.ParseTransportKind` валидирует вид из внешнего источника.
- `domain.NewTransport` — единая фабрика: по виду создаёт нужную сущность
  и проверяет инварианты, включая лёгкость использования 1..10.
  Велосипед с ненулевым расходом отклоняется.

Добавление нового вида требует сущности в домене, константы и ветки в
`ParseTransportKind`/`NewTransport`. Остальные пакеты работают с
интерфейсами и не меняются.

## Альтернативы

- **Одна структура `Transport` с полем kind и расходом 0 для велосипеда.**
  Проще, но велосипед начинает реализовывать `IConsumptor`, и расчёт
  расхода смешивает разные по смыслу случаи.
- **Отдельный сервис на каждый вид.** Дублирование сценария регистрации
  и сводки без выгоды.
- **Динамический реестр/плагины с регистрацией во время выполнения.**
  Даёт расширение без пересборки, но для трёх известных видов это лишняя
  механика и глобальное состояние.

## Последствия

- Типы проверяются компилятором; `Bicycle` не попадёт в срез потребителей
  энергии.
- Фабрика становится единственной точкой знания о соответствии
  «вид → сущность».
- Для нового электрического вида нужно реализовать `IConsumptor`; для
  неэлектрического — только `IInventoriable`.
