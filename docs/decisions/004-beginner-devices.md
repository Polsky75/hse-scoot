# 004. Лёгкость использования и подбор устройств для новичков

- **Дата:** 2026-10-25
- **Статус:** заменено ([005](005-itransport-and-inventory.md))

> Актуальная модель интерфейсов и инвентаря описана в
> [ADR 005](005-itransport-and-inventory.md). Ниже сохранено исходное
> решение для истории.

## Контекст

Нужна функция, которая возвращает список устройств, подходящих новичкам,
и суммарную потребляемую ими энергию. В модели не было признака, по
которому можно отличить такое устройство. Заказчик уточнил правило:
у каждого транспорта хранится целочисленная лёгкость использования
от 1 до 10, а значение больше 6 означает пригодность для новичков.
Геттер должен быть доступен через интерфейс транспорта.

## Решение

- В `domain.baseDevice` добавлено поле `easeOfUse int`; конструкторы
  проверяют диапазон 1..10 и возвращают `ErrInvalidEaseOfUse`.
- В `IInventoriable` добавлен `GetEaseOfUse() int`. Все виды транспорта
  на балансе реализуют этот контракт; отдельный интерфейс `ITransport`
  не вводился, потому что в сервисе нет других инвентаризуемых сущностей.
- Порог вынесен в `fleet.BeginnerMinEaseOfUse = 7` (эквивалентно
  «строго больше 6»).
- `fleet.BeginnerDevices(devices []domain.IInventoriable)` фильтрует
  по `GetEaseOfUse()` и суммирует расход только для тех устройств,
  которые дополнительно реализуют `IConsumptor`. Велосипеды попадают
  в список, но не в сумму.
- `fleet.Service.BeginnerDevices()` применяет функцию к текущему парку.
- Консольный отчёт выводит количество, ID и суммарный расход подходящих
  устройств.
- Текстовый источник получил пятое поле `ease_of_use` и валидирует его
  до создания сущности.

## Альтернативы

- **Отдельный интерфейс `ITransport` с геттером.** Семантически чище при
  появлении не-транспортных объектов на балансе, но сейчас все
  `IInventoriable` — транспорт, и дополнительный интерфейс только
  увеличил бы число приведений типов.
- **Булев флаг `beginner`.** Проще, но менее информативен: заказчик
  попросил шкалу 1..10, которая допускает более тонкую настройку позже.
- **Порог внутри консоли.** Смешал бы представление с бизнес-правилом;
  константа и функция находятся в прикладном слое.
- **Отдельный метод у каждого вида транспорта.** Дублирование и потеря
  единой точки правила.

## Последствия

- Создание любого транспорта теперь требует валидной лёгкости
  использования; текстовый формат расширен до пяти полей.
- Функция работает за O(n) и возвращает новый срез, не изменяя парк.
- Порог меняется в одном месте; при необходимости его можно сделать
  параметром DI-контейнера.
- Если появятся не-транспортные объекты на балансе, геттер стоит вынести
  в отдельный интерфейс и уточнить типы функции.
